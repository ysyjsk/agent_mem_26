# 论文证据与执行收尾
指导修订：paper-delivery-20261016。保持 focused-maintenance-v4、v13 方法与 A 的冻结矩阵；本文件是剩余科学问题、计算预算与交付的唯一细化说明，不保存运行状态。

## 1. 论文要回答的三个问题
研究对象是已有 AgentRunbook 记忆的局部观测修订维护，不是新的通用记忆架构，也不是全量冷构建加速。
1. 局部证据维护是否减少重新抽取：B3 与 Ours 同源快照配对，报告更新成本、当前事实正确性和未改事实保留。
2. 保留事件级当前证据是否有必要：Source-only 与 Ours 比较；这包含事件可用性与表示的整体作用，不能全归因于 Coalescing。
3. 合并是否优于简单追加：Overlay 与 Coalesced 在 A 同位置三轮修订中比较证据增长、实际 Reader 输入、累计更新＋查询成本和旧值误用。块数下降本身不等于端到端获益。

主张以以上机制为界。质量是成本收益的约束与解释指标，不把提高 QA 或赢过所有方法作为完成门槛。

## 2. 文献给出的实验依据
- [LongMemEval-V2 原文，§4–5 与 Appendix C](https://arxiv.org/html/2605.12493v1)：采用其 RAG 家族架构和固定 Reader 的比较思路。本项目增加历史修订接口，使用本地 text-only/adapted 设置；不能直接比较原论文的多模态、不同上下文预算成绩。Small 为每域 100 条背景历史，不是 200 个独立更新案例。
- [LightMem，ICLR 2026](https://proceedings.iclr.cc/paper_files/paper/2026/hash/a05b72653ec5b473732129829ae04195-Abstract-Conference.html) 与[论文实验表](https://arxiv.org/html/2510.18866v1)：借鉴分阶段统计 tokens、调用、耗时并与 QA 并列的做法；不能只报告被省掉的更新调用，遗漏转移到查询的成本。
- [A-MEM，消融 §4.4](https://arxiv.org/html/2502.12110v11)：组件贡献要通过匹配条件下去掉对应组件来判断。因此 Source-only 与 Overlay 解决不同归因问题；无需为此新增完整 A-MEM 框架适配。
- [NeurIPS checklist，第7项](https://neurips.cc/public/guides/PaperChecklist)及[ACL 统计检验指南](https://aclanthology.org/P18-1128/)：说明误差来源、比较单位与复现条件。重复运行不扩充独立数据样本，小样本同分或不显著不等于质量等价。

这些文献支持实验设计原则，不构成录用保证或“节省某百分比就可发表”的门槛。本研究只主张受控局部维护，不声称击败所有现有记忆架构；LightMem/A-MEM 在相关工作中比较问题与机制，不新增为当前执行 baseline。

## 3. 固定方法与公平条件
主表四行：Raw RAG、RAG+Notes、AgentRunbook-R/B3、AgentRunbook-R+Coalesced。B3 是 AgentRunbook-R 的强维护适配，不重复算一个公开 baseline。Source-only/Overlay 为机制对照；已登记辅助方法按 A 原计划完成，Delta 历史证据分版本，不增加新矩阵。

三种初始架构各构建一次、各域一份。B3/Ours/Source-only/Overlay 从同一 AgentRunbook 初始快照分出独立分支。Raw RAG/Notes 使用自身架构和正常检索，更新只处理应受影响的范围，不能故意全库重建。公共合法缓存规则一致，不能把另一方法本轮生成物当作免费历史。

保持现行模型、Reader、检索和预算。必要的运行后端修复在安全检查点进行，实际配置纳入 runtime freeze，并对适用对照一致。硬件/服务变化不能计为 Ours 的方法收益。已有语义产物可复用，跨后端计时不能混成同组配对。

## 4. 当前阻塞应如何直接处理
已知 OOM 是故障事实，不另做复现 OOM 实验，也不重复已有 dry-run/全套测试作为下一交付。恢复入口能选中失败项只解决调度；未改变失败请求的显存条件，重复提交同一请求不能算修复。
- 由执行会话在当前请求/轨迹成功持久化的安全边界，采用保持模型、精度与有效输入不变的显存措施；优先考虑现有服务的权重 CPU 卸载并预留激活/KV空间。既往 16GiB/64GiB 建议不是已验证配置，不写成已部署或必定可行。
- 修复后的第一个真实请求直接补已缺失的 Notes/Event，成功产物进入正式初始快照；不另造 smoke 请求再重复计算。恢复已确认失败的两个扩展，保留所有有效分区。
- 当前 recovery notes wrapper 捕获任意 Exception，代码没有“仅 02dad10c”限制。根据已有失败/回退记录定位基础设施错误产生的占位 Event/Notes，只补这些条目及依赖索引；不能将确定性占位笔记当作原模型生成成功，也不重建全部已完成轨迹。原架构正常的解析回退与基础设施降级分开记录。
- 原始请求已有完整输出时复用输出；缺失时补原生成路径。修复前产物保留，正式初始快照记录回退来源及修复范围。B3/Ours 的目标 Event 不能一边是正常抽取、一边是占位 fallback。
- 无法追溯的 usage 保留 unknown，并单列已知下界；不得补零。初始构建的历史 usage 不完整可以限制生命周期总成本主张，不必重跑整个库来补账。
- 后端修复/缺失条目补齐是执行恢复，不修改 v13 算法，不启动第二个 GPU 执行器。由执行会话管理服务与队列，本次文件部署不触碰活动进程。

## 7. 统一测量与统计
每条原始结果保存 unit/case/domain/method/round/repeat、数据与快照版本、实际运行配置、真实请求 IDs、答案及评分状态。
- 更新：LLM 输入/输出 tokens、调用数；Embedding calls/vectors/tokens另列；从接收修订到保存/重载后可查询的 publish wall。复制/服务启动等不在边界内的时间单列。
- 查询：retrieval controller 与 Reader 分项后求和；实际上下文 tokens、查询 wall、回答是否完整、截断/失败/待评独立记录。
- 维护总成本＝更新＋固定清单中的全部查询。初始构建单列；只有账目可比时再给“初始＋维护”生命周期数字。重试真实成本记录；请求 ID 去重；unknown不是0。
- 质量：修改事实正确、邻近/未改事实保留、旧值被误用为当前值、正常 QA 分开。只出现在 Raw State 的事实不自动说明 Event/Notes 语义正确。对预选代表案例直接查看受影响 Event/Notes，依据源证据判断事实、角色和不受支持的推断。
- 汇总：两域和支持/回退分项；报告绝对值及配对差/比率。总量降幅用同一工作负载总量之比，不能平均各行百分比后冒充总降幅。同题四方法配对正确性表保留。
- 3次计时重复报告均值、标准差及范围；跨案例成本报告每案例配对分布。重复种子/轮次不是独立轨迹。小样本不用 p95 或“未显著下降”声称质量等价；不在看完结果后设置非劣界。
- A/B 的问题重叠按ID去重展示；不要将200条背景历史、84次运行、144次回答当成质量样本量。三个连续修订点只支持观察到的增长趋势，不外推长序列极限性能。

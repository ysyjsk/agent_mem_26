# Agent Memory Construction — Research Workplan v1.0

目标会议：WWW（The Web Conference）｜阶段：Baseline 复现 → 性能分析 → 方法实现 → 论文实验

## 1. 总体方案

研究主题暂定为：

Workflow-Aware Concurrent and Incremental Memory Construction for LLM Agents

核心研究问题：

> 对持续运行的 Agent，能否利用 LLM Output、Tool Call、Tool Result 等执行事件之间的依赖关系，实现记忆的并发构建和增量维护，在保持记忆质量与一致性的前提下，降低 Memory Construction 和 Memory Freshness Latency？

  └── Tool Result

## 5. 我们的方法：具体实现什么？

方法暂定为三个组成部分，其中两个是主要创新机制。

Agent Workflow Events

LLM Output / Tool Call / Tool Result / State Transition

Memory Evidence IR

Evidence ID · Source Version · Dependency · Provenance

Mechanism 1

Concurrent Execution

根据依赖关系调度可独立处理的记忆操作

Mechanism 2

Incremental Maintenance

复用有效中间结果，仅重新处理受影响部分

Version Validation + Consistent Publication

Queryable Long-Term Memory

### 5.1 Memory Evidence IR

不直接把整个历史拼接成一个 Prompt，而是将执行事件转换为有来源和版本信息的语义单元。

例如：

```
{
  "evidence_id": "event_102",
  "source": "tool_result",
  "operation": "pytest",
  "version": 3,
  "dependencies": ["event_98", "event_101"],
  "memory_keys": ["test_status:api.py"],
  "status": "valid"
}
```

`memory_keys` 是需要由 Extraction / Reconciliation 过程确定并验证的候选依赖，不能只根据 LLM 猜测就当作完备的依赖证明。

IR 至少记录来源、发生顺序、事件依赖、内容哈希、状态版本和语义读写集合，并保留原始文本及截图引用。对于无法确认依赖的事件，采用保守的 Unknown 状态。

它的目的不是换一种格式存储记忆，而是让后续并发和增量更新能够共享一套统一的依赖信息。

### 5.2 创新点 1：Dependency-Aware Parallel Construction

例如：

```
Event 1: 查询项目 A 的状态
Event 2: 查询项目 B 的状态
Event 3: 修改项目 A 的配置
Event 4: 验证项目 A 的配置
```

理想情况下：

- Event 1 和 Event 2 可以并发 Extraction。
- Event 3、4 之间存在因果依赖。
- 项目 A 和 B 的记忆更新可能分别准备。
- 发布之前必须验证状态版本和读写冲突。

实现上采用 Dependency DAG + Bounded Task Scheduler + Version Validation。

允许独立的语义提取提前运行；对共享状态相关的合并操作，先读取一致的状态版本、生成候选更新，提交前检查版本。如果依赖被前序提交破坏，则重新计算或回退串行执行。

这里不默认“不同 Entity 一定独立”，因为两个 Entity 之间可能存在关系、别名或跨事件语义依赖。

### 5.3 创新点 2：Incremental Memory Maintenance

正常全量构建：

\\[ M\_{t+1}=\operatorname{Build}(H_t\cup\Delta H) \\]

其中 \\(H_t\\) 表示历史，\\(\Delta H\\) 是新增或修正的执行事件。

我们希望：

\\[ M\_{t+1}=\operatorname{Update}(M_t,\Delta H,D_t) \\]

其中 \\(D_t\\) 是维护的依赖索引。

具体实现：

- 对未变化、输入和环境版本相同的 Source-local Extraction 结果直接复用。
- 根据依赖索引找到需要更新的 Memory Units。
- 只重新执行受影响区域的去重、关系更新和摘要合并。
- 当依赖不明确、影响区域过大或者版本验证失败时，回退完整构建。
- 必要时重新计算关联的 Embedding 和检索索引，而不是默认全部更新。

这个设计尤其需要吸取你之前 MemBind V7 的经验：不能在原始 Graphiti Trace 上假设存在大量稳定的增量复用机会。 应先验证新的语义分层能否产生可测量的稳定性，再逐步实现局部更新。

### 5.4 实现顺序

不直接把三部分一次性写完，而是遵循：

```
Fresh Memory Construction
          ↓
Stable Evidence IR
          ↓
Parallel Construction
          ↓
Incremental Maintenance
          ↓
Dependency-Aware Scheduling
          ↓
Version Validation + Publication
```

建议优先以 Codex Native 的两阶段 Memory Write Pipeline 作为可改造候选，因为它与目标最接近。

不过最终的开发母体要在 Baseline Profiling 后确定：如果 Codex Native 无法可靠适配 LongMemEval-V2 的多模态轨迹或难以控制模型执行，则先在 AgentRunbook-R 的提取流水线上建立同算法 Fresh/Incremental 对照，再把方法移植回 Codex 风格的 Consolidation。

这一步不能为了方法方便而忽略原生系统实际的语义区别。

## 6. 测试指标：论文最终需要什么结果？

我们研究的是记忆构建效率，因此主指标必须围绕 Write Path。

### 6.1 Performance Metrics

| 指标                           | 定义                                          | 重要性     |
| ---------------------------- | ------------------------------------------- | ------- |
| P95 Memory Freshness Latency | 新证据到达至相应记忆可被一致读取的耗时                         | Primary |
| Construction Makespan        | 完成整个 History 的记忆构建和持久化所需时间                  | Primary |
| Construction Goodput         | 单位时间内成功且符合正确性要求的记忆更新数量                      | Primary |
| P50 / P99 Freshness          | 延迟分布                                        | 重要      |
| LLM Calls / Tokens           | Extraction 和 Consolidation 的实际调用与 Token 使用量 | 重要      |
| Compute Cost                 | 完成一次构建的 GPU 时间、API 费用和资源占用                  | 重要      |
| Critical Path Breakdown      | Extraction、等待、Merge、Embedding、Commit 各阶段耗时  | 重要      |
| Query Latency                | 从记忆查询得到可供 Reader 使用的证据所需时间                  | 质量辅助指标  |

Memory Freshness 必须测量到可读取的最新权威版本，而不是写入接口返回 `202 Accepted` 或任务入队的时刻。

对于官方提供的离线历史，其 Arrival Time 按固定的回放协议定义，不使用原始记录里可能相隔数天的业务时间直接计算运行时延迟。

### 6.2 Quality / Correctness Metrics

| 指标                            | 要测什么                     |
| ----------------------------- | ------------------------ |
| Official QA Accuracy          | LongMemEval-V2 总准确率      |
| Per-category Accuracy         | 五类记忆能力的准确率               |
| Current-state Accuracy        | 更新以后能否正确识别最新状态           |
| History Preservation          | 历史有效信息是否被错误删除            |
| Provenance Correctness        | 输出的知识是否具有正确来源            |
| Incremental/Fresh Equivalence | 增量维护是否与同一新算法的 Fresh 构建一致 |
| Consistency Violations        | 是否出现丢失更新、陈旧发布、重复更新或错误状态  |
| Failure Recovery              | 崩溃重试、事件重复投递、乱序完成后的正确性    |

其中 Incremental/Fresh Equivalence 需要两种验证：

1. 使用固定的模型响应 Replay，执行确定性的逐步差分对照，检查规范化的记忆状态是否一致。
2. 使用真实在线模型调用，评价质量是否下降；不能把 LLM 随机性造成的文字差异一律判为正确性错误。

主实验必须报告质量差异及其置信区间，而不是只凭 Accuracy 数字接近就宣称没有质量损失。

### 6.3 Mechanism Experiments

这部分专门解释为什么能加速。

| 变量                | 测试取值                       | 目的           |
| ----------------- | -------------------------- | ------------ |
| Concurrency Limit | 1、2、4、8、16                 | 并行扩展能力       |
| Update Ratio      | 1%、5%、10%、25%、50%、100%     | 增量收益随更新量变化   |
| Conflict Ratio    | 0%、10%、30%、50%、80%         | 状态依赖对收益的影响   |
| History Scale     | Small → Medium，及不同历史前缀     | 数据规模扩展能力     |
| Memory Size       | 不同累计记忆量                    | 增量维护随存储增长的表现 |
| Failure Injection | Worker Crash、Timeout、重复事件等 | 恢复正确性        |

Update Ratio 和 Conflict Ratio 采用 LongMemEval-V2 原始轨迹的受控重放、事件选择与变更注入构建，明确标记为 System Stress Test；不能把这些人为负载改写后的 QA 数字混入官方榜单。

除了这些常规变量，还必须记录有效增量复用率、实际失效区域比例、回退率、依赖分析开销，以及真正节省的关键路径时间。否则即便系统更快，也难以解释是否来自提出的机制。

## 7. 实验执行 Workplan

我建议按下面六个阶段推进，只有当前阶段通过 Gate 才进入下一阶段。

1. P0：固定数据集与实验环境

   锁定 LongMemEval-V2 Commit、Small/Medium Manifest、模型版本、推理服务、Judge 和统一日志格式。

   验收：数据完整性检查通过，模型服务 Smoke Test 通过，评测脚本可执行。
2. P1：官方 Baseline Reproduction

   顺序运行 RAG+Notes、AgentRunbook-R、Codex、AgentRunbook-C；然后复现 Codex Native Memories 与 MemForest 的写入流水线。

   验收：复现官方质量协议，记录差异原因；六个系统的能力边界和实验配置都有独立报告。
3. P2：Memory Write Path Characterization

   先不做优化，给 Baseline 加 Observer-only Instrumentation，测量每个阶段的耗时、依赖、LLM Calls、Tokens 和临界路径。

   验收：明确主要瓶颈在哪里，以及是否存在足够的并发和增量复用空间。若机会不足，允许得到负结论，不强行进入方法开发。
4. P3：实现基础 Memory Construction Algorithm

   构建 Evidence IR 和 Fresh Construction，先验证记忆质量，然后实现串行 Fresh 基线和并发 Fresh 基线。

   验收：新算法达到预先规定的质量要求，且并发版本不破坏状态语义。
5. P4：实现增量和依赖感知调度

   依次完成 Incremental Serial、Naive Parallel+Incremental，最后实现 Ours。每一步使用相同算法和模型做差分实验。

   验收：增量/Fresh 一致性测试通过；没有未经解释的状态错误；收益超过额外依赖分析和调度开销。
6. P5：论文级正式实验

   冻结全部配置，在 Small/Medium 和受控更新负载上进行配对重复测试，完成质量、性能、消融、扩展性、故障恢复实验。

   验收：生成主实验表、质量对比、阶段耗时分解、统计置信区间和完整复现日志。

## 8. 三个最重要的实验判断

最终能否形成较有说服力的 WWW 投稿，主要取决于这三个问题。

第一，Baseline 中是否真的存在值得优化的耗时？

如果 LLM Extraction 已完全并发，而 Consolidation 开销很小，则新增调度机制未必有意义。P2 必须先证明瓶颈。

第二，新的 IR 能否让增量维护真正减少计算？

这里需要避免此前 Graphiti 增量实验遇到的依赖放大问题。必须报告真实省掉的 LLM 工作量、失效范围、Fallback 比例和净 Critical Path 收益。

第三，相较强基线是否仍有显著收益？

我建议把研究目标设为：在相同资源预算和质量约束下，争取让 Ours 相对 Naive Parallel+Incremental 和 Codex Native，在 P95 Freshness、Build Time 或 Goodput 上产生明确且可重复的改进。可以将约 20% 的 P95 降低作为内部目标，但不能将其预设为实验结果。

最终建议：先正式冻结这份 v1.0 方案，执行到 P2 为止。 在六个 Baseline 的真实写入耗时和可并行性数据到手后，再决定以 Codex Native 还是 AgentRunbook-R 为方法实现的主代码基底。这样更可能形成一项有真实系统瓶颈支撑的研究，而不是先开发两个优化模块，再寻找能够展示加速的数据。

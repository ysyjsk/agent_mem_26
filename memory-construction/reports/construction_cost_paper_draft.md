# Draft: reducing repeated work in event-based agent memory construction

Status (2026-10-15, focused-method-v3): sections above the final focused-method section preserve historical exploration, including pre-METHOD01 snapshots with different request configurations. They are NOT the current method's main comparison or evidence of a frozen final system. Use the matched focused-method measurements below for current decisions; no broad cold-build superiority is established.

## Setting

We evaluate a text-only adaptation of AgentRunbook-R on a frozen development workload: eight official-source questions, ten complete trajectories,91 observed states,81 transitions, and20 trajectory-level notes. Each domain has one shared memory containing the evidence trajectories and fixed distractors. Queries reuse that memory rather than rebuilding question-conditioned corpora. This is not a native multimodal Small result or an official Judge score.

All variants retain the complete raw trajectories, one generated event per transition, both procedure and hint notes, their embeddings, and source mappings. The original text-only note path uses URLs, thoughts and actions; it does not reconstruct screenshot content. Controller and Reader use the same resident local Qwen3.5-9B service, with thinking disabled and fixed sampling. The embedding model is Qwen3-Embedding-8B. Single/paired event ceilings are2048/4096 tokens, while the Reader ceiling is2048. Original note requests ask for8192, but the resident service actually caps output at4096. No additional generation steps are introduced to create artificial acceleration opportunities.

## Mechanisms

Adjacent joint extraction submits two consecutive transitions in one model request. Task context and the annotated action trace are shared, and the intermediate state is included once. The model returns two separately identified events with the original overview and state-transition fields. Invalid or oversized groups split locally; successful groups are not regenerated. A singleton arrival is processed immediately, without waiting for future events.

Exact construction embedding reuse operates on the actual token-bounded text sent to the embedding model. Keys include the model, endpoint, relevant input configuration, and exact prepared text. Identical inputs share a computed vector; all original event/window source mappings remain separate. No averaging or similarity-based substitution is used.

The update comparison retains a strong B3-style exact-request cache and exact vector cache in both methods. The additional mechanism validates each output event against its own source/context dependencies, allowing a changed subset of adjacent events to be regrouped without regenerating unaffected group siblings. Both methods begin from independent copies of the same already-built snapshot. This is explicitly an AgentRunbook-R adapted mechanism comparison, not a relabeling of the historical workflow-core B3/Ours experiments.

## Measurement

Cold construction begins with empty method memory and ends after persistence and reload verification; GPU model loading is excluded because weights are resident for all variants. Two domain build wall times are summed, not summed request durations. Construction, retrieval, Reader, and subsequent update costs remain separate. Historical reused artifacts are marked and never reported as a newly measured cold build.

Client telemetry is reconciled with the resident server log: SDK automatic retries can hide multiple physical HTTP requests. Failed usage is unknown, not zero. V1 exposed128 OOM attempts arising from32 failed SDK calls. V2 therefore freezes a shared18000-token preflight rule and disables automatic controller retries; oversized single requests enter the existing12000-character/state fallback before sending. Full raw source remains queryable. This common failure handling is not attributed to either candidate.

## Preliminary results

On the first complete eight-state trajectory, joint extraction reduces event requests7→4, total controller calls8→5, and reported input tokens38824→29581 (−23.8%). Both sides preserve all seven events and both notes and pass the same five source-backed fact probes. Publication time61.20→61.51s does not demonstrate speedup: output tokens increase1528→1608, and decoding cost remains substantial.

On all five web trajectories, the matched V1 joint run reduces publication time558.09→520.17s (−6.8%) and reported successful-call input tokens252945→211444 (−16.4%). Both produce complete answers on4/4 questions with development correctness3/4. The joint run introduces two failed SDK calls/eight physical OOM attempts; their usage is unknown and excluded from the reported token totals. Thus the token result is a reduction in measured successful work, not a claim about unobserved failed compute.

The V1 ten-trajectory baseline completes in1339.04s with8/8 complete responses and6/8 development correctness. The controlled V2 four-cell matrix is in progress; do not fill unmeasured cells, claim an established best combination, or generalize the screening result to a held-out benchmark.

## Limits and next evidence

Eight development questions cannot establish statistical quality equivalence. Structural source/event checks and literal probes are complementary but not full semantic evaluation. Samples are stochastic, so a one-question difference is interpreted alongside existing matched-repeat variation. Larger-corpus repetitions, component ablations, and local-update measurements must precede a broad efficiency claim. No DAG speedup is claimed unless expensive extraction or embedding work actually decreases against valid B3 caches.

## Updated local-update main experiment (PAPER01)

We froze four complete trajectories without selecting by method outcome: two web trajectories (8 and 11 states) and two enterprise ServiceNow trajectories (16 and 15 states). For each trajectory we applied one controlled state correction and one workflow-fragment correction, choosing positions that cover both the interior and boundary of adjacent extraction groups. B3 and Ours were run from independent copies of the same combined snapshot, preserving the same exact-request and vector caches. The primary pass alternated B3→Ours; a second pass alternated Ours→B3.

All 32 paper-facing update rows (8 cases × 2 methods × 2 passes) passed source-grounded checks: the new fact was present, the original fact remained handled, untouched trajectories were unchanged, all transition source mappings were present, and Ours' reused adjacent events remained complete. These checks are not a substitute for downstream QA. A fixed Reader regression was run on one matched state-revision pair: both answers were complete and parseable, but B3 was correct (1/1) and Ours was incorrect (0/1), so the result is reported as a quality constraint rather than silently labeled quality-equivalent.

We then added two complete matched repetitions on the same eight cases, copying the same combined starting snapshot for each method and including save/reload publication. Across primary, repeat-1, repeat-2, and order-balanced repeat-3, B3/Ours cumulative update-to-publish times were 227.90/206.79 s, 208.82/175.02 s, 662.50/186.42 s, and 610.64/219.36 s; all 64 method-case run records pass source-grounded checks. Primary B3→Ours shows a modest Ours reduction (18→16 calls, 132,987→119,650 input tokens). Repeat-1 ran Ours→B3 with similar reduction. Repeat-2 also ran Ours→B3 and is retained despite the non-alternating order: B3 rebuilt 66 event outputs with 37 calls and 426,203 input tokens, while Ours rebuilt 16 with 12 calls and 97,150 input tokens. Repeat-3 ran B3→Ours and reproduced the high B3 work (66 outputs, 38 calls, 426,730 input tokens) versus Ours (16 outputs, 13 calls, 97,629 input tokens). Thus the event-level dependency mechanism's largest measured benefit appears when B3's exact grouped-request cache does not match and conservative rebuilding expands to much of the touched trajectory; on the two low-cost rounds, the difference is smaller. The complete raw per-case values and actual run order are in `results/tables/agentrunbook_update_repeat_summary.csv` and `reports/agentrunbook_update_main.md`; cumulative curves are in `reports/agentrunbook_update_cumulative.svg`.

The mechanism has a localized effect. On the short web state revision, Ours reduced wall time 44.93→19.80 s and event outputs 4→2 in the corrected rerun; on the long web thread state revision, the primary run was 13.77→19.10 s (negative wall-time result) despite 4→2 event outputs. Enterprise state revisions were near-ties (17.51→17.22 s and 14.63→14.64 s). Workflow revisions often reduced event recomputation from 3–4 to 2 and reduced input tokens when the changed position crossed a group boundary, but several enterprise cases were wall-time ties or regressions. The supported claim is therefore reduced necessary event recomputation and frequent, not universal, update-cost reduction under localized dependencies.

We separately added a same-trajectory growth case in one web and one enterprise memory, appending one arrived state to the existing trajectory (not adding a new trajectory). All eight runs passed new-fact, old-fact, untouched-trajectory, event-coverage, and persisted-reload checks. The current conservative event key includes global action/step context, so Ours exactly reused zero prior event outputs in either growth case and regenerated all 8/16 events; we retain this as a dependency-scope limitation rather than weakening the key. In the first paired pass, web publish was 149.11 s/6 calls/31,600 input tokens for B3 versus 109.92 s/5 calls/30,996 input tokens for Ours; enterprise was 168.99 s/9 calls/114,484 input tokens versus 129.85 s/9 calls/114,484 input tokens. In the order-reversed repeats, web was 61.01 s for B3 and 57.74 s for Ours (5 calls each), while enterprise was 132.15 s for B3 and 133.84 s for Ours (9 calls each). Output tokens were somewhat lower for Ours; embedding vectors were unchanged within each pair (12 and 19). The reversed repeat shows near-tie wall time, so the first-pass differences are not stable evidence of a growth speedup: no event dependency was reused.

The fixed Reader regression on the two growth snapshots covers the same four questions per domain. Every B3/Ours cell produced 4/4 complete boxed answers with zero truncation, service failure, or parse failure; both methods scored 3/4 in web and 3/4 in enterprise. Query/prompt preparation is reported separately (88.04 vs 532.52 s on web and 283.61 vs 137.53 s on enterprise) and is excluded from the construction-cost claim because it is highly variable and not an update-stage measurement.

For the eight fixed state/workflow revision cases, the no-build-cache Fresh/B0 touched-partition rebuild reference totals 1,249.20 s, 56 controller calls and 589,121 known controller-input tokens. Matched B3 totals 227.90 s, 18 calls and 132,987 input tokens; Ours totals 206.79 s, 16 calls and 119,650 input tokens. These are sums of eight per-case wall times, not a concurrent elapsed duration. All 48 saved Fresh/B3/Ours case records pass source-grounded update checks and persisted reload; Fresh is explicitly a touched-partition rebuild, not a full-domain cold build. The per-case cumulative comparison is in `reports/agentrunbook_update_fresh_comparison.svg`, while `reports/agentrunbook_update_cumulative.svg` retains B3/Ours primary and order-reversed repeated costs.

The state-revision Reader regression reuses four fixed questions per domain on persisted memories, with a 2,048-token local Qwen Reader and no thinking. All 36 responses are complete and parseable, with no truncation, service or parse failures. Web scores are 3/4 for Fresh, B3 and Ours; on the representative enterprise state revision, Fresh and Ours score 2/4 while B3 scores 3/4 in both repeats. This local gap is a quality constraint: structural/reload checks alone do not prove downstream quality preservation. We then extended the same fixed four-question domain sets to all eight state/workflow revision snapshots for the matched B3/Ours methods. Across 64 answers, both methods score 21/32 (web: B3 12/16, Ours 13/16; enterprise: B3 9/16, Ours 8/16); all 64 are complete/parseable with zero truncation, service or parse failures. This broader adapted-local proxy shows no aggregate score difference, but is too small and source-specific to establish non-inferiority. Fresh/B0 was not read on every workflow case and is therefore excluded from the eight-case matched QA comparison. None of these are native Small or official Judge results. Per-case detail is in `results/tables/agentrunbook_revision_case_reader.csv` and `reports/agentrunbook_revision_case_reader.md`.

## Common-preflight cold-construction candidate (PAPER02)

The only new cold-build factor applies the existing bounded-state preparation to joint requests before deciding whether two adjacent transitions fit the 18,000-token safety budget. A pair is sent jointly only after this preparation; otherwise the group splits locally into single events. On the two most frequently split enterprise trajectories (`0ab99e0c`, `49f98e9e`), the baseline took 741.94 s with 35 controller calls (2 failed/retried), 291,019 known LLM input tokens, and 13,848 output tokens. The common-preflight joint candidate took 412.44 s with 19 successful controller calls, 209,996 input tokens, and 11,575 output tokens: −44.4% wall time, −34.8% input tokens, and 14 successfully parsed joint groups. Both variants published all 29 expected events, retained 62 embedding vectors, and passed save/reload and source-coverage checks. This result supports retaining the candidate for fixed-10 expansion; it does not claim unchanged downstream QA beyond the reported structural checks.

Paper-facing files are `results/tables/agentrunbook_update_main.csv`, `reports/agentrunbook_update_main.md`, `reports/agentrunbook_update_cumulative.svg`, `results/tables/construction_pair_v3_common_preflight.csv`, and `reports/construction_pair_v3_common_preflight.md`.

## Scale and component ablations (PAPER04 draft)

The frozen four-cell 10-trajectory construction matrix does not identify a wall-time win for the candidate components. Baseline is 830.00 s (93 controller calls, 735,023 input and 18,603 output tokens, 192 embedding vectors). Joint extraction alone reduces calls to 78 and input to 686,954 tokens, but takes 1,025.77 s; exact construction-embedding reuse alone reduces vectors from 192 to 184 but takes 882.95 s; their combination takes 989.91 s with 76 calls, 666,712 input tokens and 184 vectors. All rows pass structural/fact-probe checks. The combined candidate therefore lowers calls by 18.3% and known input tokens by 9.3%, while increasing wall time by 19.3% and output tokens; it is not selected as a practical cold-build improvement.

At the larger 24-window/60-checkpoint scale, the serial full-prefix B0 totals 1,268.67 s, compared with 476.22 s for Ours-dev and 473.99 s for strong B3-c2. Ours-dev and B3-c2 have identical measured controller calls (205), input/output tokens (412,723/17,120), and embedding calls; the 2.23-second wall gap favors B3 and is not evidence for Ours. At 12 windows/36 checkpoints, B3-c2 and Ours-dev are also near-identical at 292.72 and 293.22 s, with all 36 snapshots validated. The reported 24-window B0/Ours/B3 runs all validate 60/60 checkpoints. These construction_e2e measurements are development-scale costs, not official QA or streaming Freshness.

The eight revision cases also expose observed recomputation strata from about 0.13 to 0.39 of the original trajectory's event count. They are descriptive case-level bands, not a controlled randomized update-rate sweep; that stronger scale claim remains open. ## Focused method: version-aware source-delta maintenance (development draft)

Our current hypothesis is that a local observation correction need not trigger another complete reading of its pages or regeneration of every event in the original extraction group. We retain the existing event interpretation as explicitly historical for the revised fields and publish exact corrected observations with source-state and pre/post-transition roles. The attempted action and unchanged neighboring observation remain distinct: changing a pre-state is not evidence that the action produced that change. Events, procedure/hint notes, raw evidence, original source mappings, embeddings and the queryable index remain available. Unsupported source/dependency changes fall back to ordinary extraction. This is a restricted maintenance mechanism, not a substitute for semantic repair on arbitrary tasks.

Event-level dependency validation reuses unaffected group outputs. A coalescing candidate additionally replaces accumulated CURRENT evidence blocks with one current view: it retains source-exact lines at the same state, removes superseded lines, and unions the latest corrected and neighboring evidence. Original historical prose is retained with a single supersession label, rather than repeatedly nested. No new compression model or similarity-based cache validity test is used. The merge therefore aims to bound repeated-update evidence/embedding work and prevent old patches from still claiming to be current. Both zero-model variants already avoid update LLM work; coalescing cannot be credited with an additional reduction below zero.

Strong B3 reconstructs the touched trajectory through all of its legitimate exact request and vector caches. It receives the same bounded event-input preparation and source-scoped current-evidence publisher. Our narrow additional mechanisms are event-level reuse and version-scoped source maintenance instead of newly generated interpretations. A semantic-edit comparator uses the old event, exact source changes and unchanged-neighbor context to request minimal literal edits. We do not remove global action-trace/step dependencies to manufacture hits. METHOD01 construction-matched snapshots and actual persisted outputs bind cache entries to their generating requests/source; sequential runs now persist the newly published output/source binding instead of incorrectly carrying an old provenance digest forward.

### Current measured evidence, not a frozen final claim

Four controlled corrections span two web and two enterprise trajectories in the complete shared domain histories. The four independent updates require 66,476 LLM tokens and 112.050 seconds in strong B3, 5,773 tokens and 44.369 seconds with guarded semantic editing, and zero update LLM tokens and 7.124 seconds with the versioned source overlay. These are sums of per-case publication wall times, including save/reload, not concurrent request duration sums. Embedding computation is nonzero and remains in the raw tables. Earlier reply/count update costs are reused historical measurements, while the Title/sort updates and normal retrieval validation were completed in the current continuation.

On frozen normal retrieval, overlay and edit each answer all eight controlled changed-fact/preservation probes correctly. B3 produces seven correct answers and one truncated, unscored answer; we do not report this as full-scored accuracy. The latter question calls a posted paragraph a preview, a pre-existing wording issue retained for all branches and explicitly limiting attribution of this failure. Ordinary four-question-per-domain regression repeated over the four snapshots yields 14/16 for overlay and B3 and 13/16 for edit; all48 regression answers are complete. These repeated development questions do not establish statistical quality equivalence. Generated-event source roles and all affected generated notes were inspected; notes describe intended workflows rather than asserting the revised observed values. The retained prior event prose remains a limitation that the sequential and semantic-confirmation cases must test.

The provisional decision is to remove always-on semantic editing for these source corrections. The current next experiment uses three sequential revisions in each of two predeclared cases, with each method carrying its own real published history and legal caches. Every round includes the same two normal retrieval probes, and cumulative cost includes query planning, query embedding and Reader work separately from updates. It tests current-evidence coalescing against both the overlay ablation and strong B3. Results and cumulative plots are generated by tools/report_method_v13_sequence.py; semantic rejection/selection-mismatch cases then determine whether any selective model repair is necessary. No new external framework is a prerequisite.

Scope boundaries: these are adapted text-only controlled source corrections, not native Small, official Judge evaluation, independently drawn quality samples, or proven same-trajectory growth/cold-construction speedups. Raw RAG and RAG+Notes remain cheaper historical cold-build references. No superiority to them, or broad novel-method claim, follows from this event-memory maintenance result alone.
